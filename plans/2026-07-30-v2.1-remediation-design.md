# Quick I Ching V2.1 Remediation Design

## Objective

Move the current production-shaped MVP to a fail-closed, transactionally correct implementation without collapsing the independent casting, risk, generation, entitlement, review, and privacy lifecycles.

## Delivery model

The remediation is delivered as six stacked draft pull requests so each subsystem can be reviewed and rolled back independently:

1. Reveal, Login Intent, key management, cancellation semantics, and CI.
2. Risk clarification/classic-only paths plus structured Preview/Reading output.
3. Server-authoritative wizard recovery, entitlement, review, history, and privacy lifecycle services.
4. PostgreSQL schema, deterministic migrations, and transactional repository adapters.
5. Better Auth and Creem payment/webhook integrations.
6. Durable generation jobs, production AI provider, traceability, and release verification.

Each branch is based on the preceding branch until the stack is merged.

## Cross-cutting constraints

- `docs/` remains limited to `PRD.md` and `技术设计文档.md`; working plans live under `plans/`.
- No anonymous response contains result, preview, report, or question fields before a committed reveal.
- Browser state never authorizes ownership, lifecycle, risk, payment, generation, or report content.
- Every external input and generated output is validated at its boundary.
- Production configuration has no local, in-memory, simulated, or deterministic fallback.
- Unknown exceptions are logged with non-sensitive metadata and rethrown.
- All behavior changes are test-first and verified by GitHub Actions before a PR is marked ready.

## PR 1 design: reveal and identity continuity

### Keyring

Runtime configuration becomes the source of truth for purpose-separated keyrings. Local/test mode uses explicit deterministic development keys only inside the local adapter. Production requires configured versioned keys. Crypto APIs receive a keyring or resolved key material rather than reading `APP_SECRET` internally.

A fingerprint keyring has:

- `read`: all accepted versions;
- `writeVersion`: one cluster-wide version;
- one write version remains stable for at least the 72-hour lock window during rotation.

### Login Intent

A Login Intent stores an opaque ID, casting ID, anonymous owner hash, nonce hash, approved callback path, expiry, consumption time, and creation time. Raw nonces are returned once and never stored.

Starting an intent verifies anonymous ownership and an awaiting-reveal casting. Consuming it atomically:

1. verifies the authenticated user and nonce;
2. verifies expiry, single-use state, callback path, anonymous owner, and casting lifecycle;
3. computes candidate fingerprints for all read versions;
4. serializes the per-user/per-question decision;
5. marks duplicates without exposing their result fields;
6. binds and reveals the winning casting;
7. consumes the intent in the same transaction.

A different browser may complete a valid Magic Link or OAuth callback and continue there. The original anonymous browser receives no result access unless it also has the authenticated session.

### Cancellation semantics

Replacing an untouched draft does not use `user_deleted`. Untouched drafts transition to `cancelled`; privacy deletion remains represented only by `user_deleted`.

### CI

GitHub Actions runs install, lint, typecheck, unit tests, and a credential-free build/contract gate. Database and live-provider tests remain explicit conditional jobs.

## Remaining PR boundaries

PR 2 owns deterministic risk routing and validated classic/AI output. PR 3 owns UI recovery and business lifecycle services. PR 4 owns database correctness. PR 5 owns real authentication and payments. PR 6 owns durable execution and production release evidence.
